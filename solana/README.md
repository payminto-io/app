# payminto-receipts (Solana program)

`payminto_receipts` is a small Anchor program for direct-to-merchant invoice payments on Solana with on-chain idempotency.
It is the Solana twin of the Tempo memo rail: the payer pays the merchant directly, and the chain itself records which invoice was paid.

## What it does

The program has one instruction, `pay_invoice(invoice_id: [u8; 32], amount: u64)`.
It transfers `amount` of an SPL token from the payer's token account to the merchant's token account with a `transfer_checked` CPI.
In the same transaction it creates a `Receipt` PDA seeded by `["receipt", merchant, invoice_id]`.
The receipt stores the invoice id, payer, merchant, mint, amount, slot, unix timestamp and bump.
Because the receipt is created with `init`, a second payment for the same merchant invoice fails and the whole transaction reverts, so an invoice cannot be paid twice.
Every successful payment emits an `InvoicePaid` event.

Checks enforced on-chain:

- `amount > 0` (`ZeroAmount`).
- Both token accounts use the payment mint (`MintMismatch`).
- The payer token account is owned by the payer (`PayerOwnerMismatch`).
- The merchant token account is owned by the merchant (`MerchantOwnerMismatch`).
- The mint and both token accounts belong to the supplied token program (classic SPL Token or Token-2022).

There are no admin keys, no config accounts, no fees and no custody.
Funds never touch a program-owned account.

## How it relates to the gateway

Payminto is non-custodial software: the merchant receives funds directly and Payminto only verifies them.
For a Solana invoice, the Go backend can derive the Receipt PDA from the merchant address and the 32-byte invoice id (for example the SHA-256 of the Payminto invoice id).
If the account exists and its mint and amount match the invoice, the invoice is paid, with no log scraping or memo parsing.
The `InvoicePaid` event gives a push signal for indexers that prefer to subscribe instead of polling.
Wiring the backend and checkout to this program is the next step and is not part of this change.

## Layout

- `programs/payminto-receipts/src/lib.rs` - the program (141 lines including comments, about 110 lines of code).
- `tests/payminto-receipts.ts` - Anchor TypeScript tests against a local validator.
- `Anchor.toml` - the Anchor workspace, with test validator ports moved off 8899 so tests never collide with a running demo validator.

## Build and test

Requirements: anchor-cli 0.31.1, Solana (Agave) CLI 2.3.x with `cargo-build-sbf`, and Node.js.

```sh
cd solana
npm install
anchor build
anchor keys sync   # first build in a fresh clone only, see below
anchor test
```

The program keypair lives in the git-ignored `target/deploy/`, so a fresh clone generates a new one on the first build.
`anchor keys sync` writes that key into `declare_id!` and `Anchor.toml`; do not commit that local change.

`anchor test` starts a throwaway local validator on port 18899, deploys the program and runs the suite.
It never talks to devnet or mainnet.

The suite covers:

- Happy path: balances move and every receipt field is correct, and the `InvoicePaid` event fires.
- Paying the same invoice twice is rejected and the merchant balance does not change.
- A token account with the wrong mint is rejected and no receipt is created.
- A merchant token account not owned by the merchant is rejected.
- A zero amount is rejected and no receipt is created.
- Payment with a Token-2022 mint works through the same instruction.

## Toolchain note

`Cargo.lock` is committed on purpose.
The Solana platform tools ship Cargo 1.84, which cannot parse crates that use edition 2024.
The lockfile was generated with the MSRV-aware resolver and `blake3` is pinned to 1.5.5 so the SBF build resolves.
If you regenerate it, run `CARGO_RESOLVER_INCOMPATIBLE_RUST_VERSIONS=fallback cargo generate-lockfile` and then `cargo update -p blake3 --precise 1.5.5`.
The one remaining compiler warning (`AccountInfo::realloc` is deprecated) comes from code generated by anchor-lang 0.31.1, not from this program.

## Known limits

- The caller supplies `invoice_id`, mint and amount without a merchant-issued quote authorization. A first call with an incorrect amount or token can occupy the receipt PDA for that invoice; authorized quotes and recovery are required before gateway integration.
- Token-2022 mints with a transfer fee deliver less than `amount` to the merchant, while the receipt records `amount`; the verifier should check the received amount for such mints or reject them.
- Token-2022 mints with a transfer hook are not supported because the instruction does not forward extra accounts.
- The program id in `declare_id!` is a local key; a devnet or mainnet deployment needs its own keypair and `anchor keys sync`.
